Architecture Atlas · matching, anomaly rules, AI layer and review UI, production hardening, real-data trial kit and a public-data evaluation built (milestones 1-9); a trial on your own statements and deployment are not done

Matchbook

Reconciliation and fraud flagging for small merchants and individuals. You bring a bank or UPI statement and your own records; it tells you what matches, what doesn't, and what looks wrong. It runs entirely on your machine and reuses Tessera's warehouse, job runner, SQL guard and local-model gateway.

The problem, and who has it

PainEvidenceConfidence
Scams and duplicate or unauthorised debits go unnoticedFinance Ministry data to Parliament: UPI fraud cases 4.07 lakh (2021-22) to 13.42 lakh (2023-24); a LocalCircles survey found 51% of victims never filed a complaintHigh (official + survey)
Matching bank, gateway and books by hand eats timeVendor blogs claim 20-40% of finance time and 10-15% error ratesLow (vendor claims, no independent source)
Small firms live in spreadsheetsVentana: 62% of SMBs use spreadsheets as their only analytics tool (dated, about 2020-22)Medium

Primary users

  • Small merchant (shop, online seller): sales records on one side, gateway settlements and bank credits on the other. Settlements arrive batched and net of fees, so nothing matches one-to-one.
  • Individual or household: a card/UPI statement to scan for duplicate charges, forgotten subscriptions, unfamiliar payees and refunds that never arrived.
What this is not. It is not a bank-grade fraud engine and does not stop transactions in real time. It reviews statements after the fact. Detection is rules and robust statistics, not a trained model, because there is no labelled fraud data to train on.

System context

Files in, answers out, nothing leaves localhost. Statements are sensitive, so the only network call is to Ollama on 127.0.0.1.

The matching engine

Matching is deterministic and explainable. A model is never the one that decides a match; it only helps a human review what the passes could not settle.

PassRuleHandlesAuto-accept?
A · ReferenceSame extracted reference/UTR/order id and same amountClean one-to-one paymentsYes
B · Amount + windowSame amount, posted within ±3 days, payee similarity above threshold (token-set ratio on cleaned names); unique best candidate onlyMissing references, timing lagYes if unambiguous
C · Settlement batchOne bank credit = sum(gateway orders) − fees − refunds, within a stated tolerance; bounded subset search over a date windowGateway payouts, the main merchant headacheOnly if the difference equals reported fees
D · Fuzzy residualRank remaining candidates by amount distance, date distance, name similarity, memory of past confirmationsEverything elseNever: goes to the review queue

Outcomes

matched · matched_with_difference (fees, rounding, with the amount shown) · unmatched_bank (money moved, no record) · unmatched_ledger (recorded, never arrived) · duplicate.

Why subset-sum is bounded. Pass C is NP-hard in general. It is capped (window of days, maximum batch size, time budget) and reports "gave up" instead of guessing, so an incomplete search is visible rather than hidden.

Anomaly & fraud flagging

Every flag carries the rule that fired and the numbers behind it. The assistant can rephrase a reason, but it cannot create one.

RuleFires whenTypical real cause
Duplicate chargeSame payee and amount twice within a short windowDouble-tap, retry, genuine double billing
New payee, large amountFirst payment to a payee and amount above a robust threshold for this accountScam, mistaken transfer
Outlier for payeeRobust z-score (median/MAD) vs. that payee's historyPrice hike, billing error
VelocityMany small debits in a short spanCard testing, drained account
Just under a limitCluster of amounts just below a known cap (e.g. ₹10,000)Structuring, limit probing
Orphan refundCredit labelled refund with no original debitReconciliation gap
Unfamiliar hourActivity outside the account's usual hoursCompromised credentials
Subscription driftRecurring payee whose amount rose or cadence changedSilent price increase

Scores combine rules into a ranked list; thresholds are per-account and tunable. Each "dismiss" or "confirm" is stored as a label so thresholds can be adjusted from the user's own history.

Honest limit. These rules find unusual and duplicate activity, not proven fraud. Expect false positives on legitimate one-off purchases. Precision is measured, not assumed (see Evaluation).

Built and measured: the AI layer (local qwen2.5:3b on CPU)

1. Column mapping. Rules run first; the model is asked only about the fields the rules cannot settle, in plain text (a 3B model parroted JSON input back at first). Every proposal is validated against the data: columns exist, dates and amounts parse, order ids are unique, the running balance follows debits and credits (catches swapped columns), and gross ≥ net ≥ fee ≥ tax for gateway files. The user still confirms.

SetApproachLayouts fully rightFields rightWrong but passed validation
Dev, 15 layouts*Rules only3 / 1557 / 87 (66%)0
Model only10 / 1571 / 87 (82%)0
Rules + model + validation13 / 1585 / 87 (98%)0
Held-out, 6 layoutsRules only3 / 623 / 37 (62%)0
Model only4 / 626 / 37 (70%)0
Rules + model + validation5 / 636 / 37 (97%)0

*I tuned the prompt and validators while looking at 4 of the dev layouts, so treat the dev row as optimistic and the held-out row (written afterwards, never tuned against) as the fair one. Average time about 4-5 s per file. The misses were optional fields (balance, payment reference, one gateway column) left unmapped; the single held-out miss was flagged by validation. The layouts are ones I wrote, so this measures robustness to header and format variety, not to every real bank.

2. Masking. Account, card, phone and long reference numbers, emails and UPI handles are redacted before any prompt; amounts and dates are kept. The gateway has a strict mode that independently re-scans every message and refuses to send if anything identifier-like is left, so masking cannot be skipped by a future code change. A test feeds real narrations (which contain 10-digit references) through the mapping path and asserts none reach the model.

3. Flag explanations: the model is opt-in, the template is the default. A first version checked only that every number in the model's text appeared in the evidence. Reading the outputs showed that is not enough: texts passed while saying the account balance rose 25% (it was the price), that the shop owner received five payments (they were made), or that payees were customers. The guard now also requires the core amounts and payee name to survive and rejects reversed-direction words, foreign currency and truncation. On a statement none of this was tuned against, 10 of 32 rewordings were accepted and 22 fell back to the template; I read the 10 and judged 9 faithful and 1 repetitive. That is my own judgement on a small sample. The default explanation therefore stays the deterministic template, which is always correct; the rewording is an opt-in extra and is labelled as such.

Things the AI layer taught me, recorded because they are the real findings. (a) Number-grounding is necessary but not sufficient: a model can reuse a real number in a false sentence. The role-word check is a targeted patch, not a general fix. (b) The explanation cache was first keyed by row id, which repeats across statements, so one statement's explanation could appear on another's transaction. It is now keyed by a hash of the evidence, with a regression test. (c) A test showed the gateway amount check accepted swapped fee and net columns, because the identity gross − fee − tax − net = 0 is symmetric. An ordering check closed it. (d) A 3B model is useful where its output is checked against data (mapping) and weak where it is asked to restate findings in free prose.

Hard rules

  • The model never does arithmetic on money. Totals, differences and fees come from SQL over integer paise.
  • The model never confirms a match or dismisses a flag.
  • Account and card numbers are masked before any text reaches a prompt.

Ranked by score, the top 20 flagged rows were 70-95% real across seeds, the top 100 about 83-87%. Threshold sweeps show the trade: for just_under_limit, requiring 5 payments instead of 3 lifts precision from 82% to 100% but drops recall from 100% to 68%; for new_payee_large, the 95th-percentile threshold lifts precision to 90% at 76% recall.

Read these carefully. Perfect recall is partly circular: the injected anomalies were written to match each rule's definition, so it shows the rules are implemented correctly, not that they find real fraud. The informative column is precision, which falls once legitimate look-alikes are present, and real statements will have more of those than my generator does. The first version scored near 100% everywhere because the injected anomalies were too easy; adding unlabelled "hard negatives" is what made the evaluation honest.
What these numbers do not show. They come from a generator I wrote, so they prove the engine handles the faults I thought of. They say nothing yet about real bank formats or real gateway quirks. Refunds, partial payments and multi-currency are not modelled.

A reconciliation tool that is "probably right" is worse than none. Accuracy is measured against known answers.

Built: the review UI (./run_matchbook.sh, http://127.0.0.1:8788)

Design decisions. Decisions are an append-only event log per item; undo pops one step (so confirm → reject → undo returns to confirm), and undoing a link actually removes it and re-runs matching. Items are keyed by stable identifiers (order id, payment id, or a hash of date, payee and amount), not row ids, so decisions survive re-importing the same statement. Uploads are raw bodies saved under a fixed server-side name, with a 50 MB cap, so a client can never choose a path.

Verified. 10 API tests (61 in the full suite) cover the flow, bad-mapping refusal, security edges, stable keys, and link/undo reversing the match counts exactly. I also drove the real screens in a browser: messy-header demo → AI mapping → fixed one unmapped optional field by hand → import (4,000 orders, 97.0% auto-matched) → confirm with note → undo → link → undo.

Defects this build surfaced, kept here because they are the honest record. (a) Before the first import, read endpoints returned HTTP 500; they now return empty results. (b) The live-validation endpoint failed with 422 because its request model was declared inside the app factory, which FastAPI cannot resolve under postponed annotations. (c) After linking an order, the Linked tab was empty because it read from the exceptions table, which no longer contained the order, so Undo was unreachable from the UI. It now reads from the manual links. (d) Navigation links were unreadable in dark mode. All four were found by using the UI, not by the earlier tests, which is why the end-to-end browser pass mattered.
Not verified. Behaviour with hundreds of thousands of exceptions in the browser (the API pages results, but I have not timed the UI at that size); more than one reviewer at a time (single user, no authentication, DuckDB single writer); mobile layouts; keyboard shortcuts do not exist yet. I tested in one browser pane only.

Found while building it, kept as the honest record.

  • SQL injection through CSV column names. Header names were pasted into SQL in several places. A header that closed the quote could have run arbitrary DuckDB SQL (which can read local files). Every identifier is now quoted and a regression test uses a real hostile header. Found by the security linter while fixing something else, not by planning.
  • Python 3.11 breakage. The importer used backslashes inside f-string expressions, a syntax error before 3.12, while the package declared support for 3.11. It only worked here because this machine runs 3.14.
  • File names became table names in the Tessera ingest step. Now allow-listed, with a test.
  • A vulnerable dependency (certifi) found by the audit; upgraded and given a version floor.
  • My own regression: replacing the matching call in the import path with a link-sync meant the first import produced no exception queues. Caught by the tests.
  • CI would have failed on every run: the dependency audit tried to look up this project on PyPI. Fixed after running the audit locally.
  • Smaller: an empty "Linked" list earlier, cached stylesheets after an upgrade, the login form keeping the last username, and an unstyled password box.
Known gaps. This is a hardened prototype, not a deployed service. (1) No TLS in the app: it must sit behind a reverse proxy, with the Secure cookie flag turned on. (2) The audit chain detects edits but cannot stop someone with full database-owner rights from rewriting the whole chain; real protection needs the latest hash published somewhere they cannot reach. (3) No MFA, SSO or self-service password change or reset; admins set passwords. (4) The login throttle is in memory, so it is per process and weak behind a proxy that hides client addresses; the per-account lockout is in the database and does hold. (5) One database role runs both migrations and the app; production should separate them and grant least privilege. (6) DuckDB is still a single-writer file, so the app cannot run as several replicas, and there are no backups, encryption at rest, retention policy or monitoring. (7) Not tested: load or concurrency beyond the race tests, a browser other than the built-in one, and any real bank or gateway data. (8) Dev users are created with random passphrases stored in a git-ignored, owner-only file; a real deployment must create users with the admin CLI instead.

Built: real-data trial kit

Your own statements have no answer key, so the kit estimates accuracy from a random sample you label by hand and reports it with a confidence interval. Guide: docs/real-data-trial.md. It runs on DuckDB alone (no login, no Postgres, no model server).

StepToolWhat it does
Maskmask_toolKeyed-HMAC tokens, so the same payee or UTR gets the same token in every file (repeat-payee rules and cross-file joins keep working) and cannot be reversed without the key. Scans its own output for what is still visible. Cannot be perfect on free text.
Checktrial preflight, normalizePreamble/footer lines, newest-first order, ambiguous dd/mm dates, decimal commas, currency symbols, single-amount layouts, missing pages (balance breaks), month gaps, duplicate ids, delimiter, encoding.
Tie outtrial load, tieoutFour control-total identities that must hold exactly, plus the match rate by value as well as by count.
Sampletrial sampleDeterministic stratified random sample per rule, queue and flag type, with per-rule sizes so labels go where the risk is.
Scoretrial score, reportWilson intervals per group (exact bound at zero events), a stratified population estimate with finite-population correction and a deliberately conservative upper bound, and a report that states its limits.

The kit itself was validated before being offered. Simulated 95% intervals contained the truth in at least 95% of 1,500 trials in three scenarios, including rare events and a tiny bad group. On a synthetic scenario with known answers, intervals computed from labelled samples contained the true wrong-match rate and the true missed-match share for three different random samples. Each preflight check is tested against a planted instance of the problem it claims to find. 23 tests.

What using it on a synthetic scenario showed. With 25 labels per rule the scorer will not claim better than "0% to 11.3% wrong", even though the true rate was about zero. That is correct: 25 clean samples cannot support "under 1%" (that needs 299), and the tool says so instead of printing a flattering 0%.

Reading it: the matcher stays precise even with no references because ambiguous cases go to the review queue instead of being guessed; the cost is recall, which falls to 86% when orders are single-item, prices repeat, and no payment references exist. That dependence on references is the main practical finding. Real data was also less ambiguous than my synthetic price catalogue, so the earlier synthetic benchmark was the harsher test on that dimension.

Not evaluated on public data. Anomaly rules: no public dataset I could reach without a login has statement-level payees plus fraud labels, and the common card-fraud sets lack payees entirely, so those rules are still tested only on injected anomalies. This retailer sells largely to trade customers, so its invoice totals vary more than a consumer shop's would. The fault model (capture 0-1 days after the order, T+2 settlement, my fee structure) is mine.

Found along the way. The two worksheets overlap by about a week: 34,337 duplicate rows would have been double counted. Preflight missed a missing page of a statement (only one broken balance step, below my 98% threshold) until a test exposed it; any break is now reported. The masker's own scanner flagged its tokens about 1% of the time (hex tokens that happened to be all digits), which would have trained users to ignore it; tokens are now letters-only. The same regex exempted a long number directly after a comma or period from masking, in both the masker and the gate that protects model prompts, a real leak, now fixed with tests. Output folders were read at import time instead of call time. The package's editable install had silently lost its path file, so modules only ran from the project folder. A second Python 3.11 f-string incompatibility was caught by the linter.

Out of scope for v1

  • Scanned or PDF statements (needs OCR; high error risk). CSV/XLSX only.
  • Live bank connections and account-aggregator APIs.
  • Real-time blocking of transactions.
  • Trained fraud models; needs labelled data we do not have.
  • Multi-user access and authentication.
